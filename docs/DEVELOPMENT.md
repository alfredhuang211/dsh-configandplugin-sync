# Development, release and publishing

How to change this plugin, verify it, and ship a version. Written for whoever
picks this up next, including a future me.

> Every command here was run on this repository. If one stops working, fix the
> document — a runbook that lies is worse than none.

---

## 1. What this package is

A **DSH bundle**: an npm package whose `package.json` declares `dsh.bundle`, so
that installing it adds a configuration layer to a DSH profile.

```
package.json          name, exports, dsh.bundle / dsh.client, engines.dsh
cordis.patch.yml      the layer: which rows the bundle inserts into a profile
lib/                  built host half (committed — see §3)
client/bundle.js      built browser half (committed)
locale/{en,zh}.json   display title/description for the Plugins page
icon.svg              Plugins-page artwork
```

Key constraint: **the consumer's pnpm blocks dependency build scripts**, so a
Git install must carry the built output. That is why `lib/` and
`client/bundle.js` are committed even though they are generated.

## 2. Everyday development

```bash
npm ci                  # install exactly what the lockfile pins
npm test                # the suite
npm run build           # rebuild lib/ and the browser half after source edits
```

`npm ci` runs against `package-lock.json`; never commit a hand-edited lockfile —
regenerate it with `npm install` and review the diff.

### Editing the host half

Source lives under `src/`; the TypeScript build writes `lib/`. Keep the two in
sync in every commit that changes behaviour — a stale `lib/` is what a Git
install actually runs.

### Editing the browser half

The client bundle is generated by a script and must keep the exact shape the
Harness module table expects: `window.__ModuleLoader__.load({ id, factory })`,
where **`id` must equal the package name**. If you rename the package, that id
must move with it, and a test asserts it.

### Editing the bundle patch

`cordis.patch.yml` inserts one row. Two identifiers matter and only one follows
the package name:

| Field | Follows the package name? | Why |
|---|---|---|
| `name` | **yes** | Node has to resolve the module by package name |
| `id` | **no** | it is the profile override key; renaming orphans user overrides |

`name:` must be **quoted** when it starts with `@`: `@` is a YAML reserved
indicator, and an unquoted value fails to parse, which silently disables the
whole bundle.

### Editing display metadata

`locale/en.json` and `locale/zh.json` carry `meta.title` and
`meta.description`, read by the Plugins page **without activating the plugin**.
English titles use sentence case. Both files must exist and export
`./locale/*.json`; the icon must be exported as well, be SVG/PNG/JPEG/WebP, and
stay under 256 KiB.

## 3. What must stay consistent

Changing the package name touches more than `package.json`. The rule that keeps
this safe:

**Module identifiers follow the package name. On-disk and on-wire state does
not.**

| Identifier | Where | Scope | Why |
|---|---|---|---|
| package `name` | `package.json` | scoped | consumed by npm and Node |
| row `name` | `cordis.patch.yml` | scoped | resolved as a module |
| client bundle `id` | `lib/client.js` (generated) | scoped | must equal the package name |
| locale namespace | `src/constants.ts` `LOCALE_NS` | scoped | a namespace is an opaque string |
| row `id` | `cordis.patch.yml` | unscoped | profile override key |
| data directory | `src/constants.ts` `APP_DIR_NAME` | unscoped | `$DSH_HOME/dsh-configandplugin-sync/`; renaming orphans the stored passphrase and `config.json` |
| HTTP route prefix | `src/http/api-types.ts` | unscoped | `/api/dsh-configandplugin-sync`, the contract between the two halves |

The 0.1.0 → 0.2.0 rename moved the first four and deliberately left the last
three. That is why upgrading an existing install only means reinstalling the
bundle: nothing on disk or on the wire moved.

## 4. Versioning and `engines.dsh`

`engines.dsh` declares which Harness versions this package accepts. Two traps:

**Prereleases need an explicit branch.** node-semver only lets a prerelease
satisfy a range when a comparator on the *same* `major.minor.patch` tuple
carries a prerelease tag. So:

```
>=0.2.0-rc.1 <0.3.0                        ✗ rejects 0.2.3-alpha.2
>=0.2.0-rc.1 <0.3.0 || >=0.2.3-alpha.2 <0.3.0   ✓
```

This package uses the second form. DSH's own check runs with
`includePrerelease`, but a user's plain `npm install` does not — the first form
would fail there while passing in DSH.

**When `engines.dsh` is present it alone decides**; peer ranges are then
ignored, and an empty or invalid range rejects every version.

Semantic versioning: a rename or a dropped identifier is breaking; new metadata
is not.

## 5. Release checklist

```bash
npm ci
npm test
npm pack --dry-run          # runs prepack: a full rebuild, then lists the tarball
```

Before every release, confirm the pack list contains:

- `lib/` (or `client/`) — the built half;
- `cordis.patch.yml`;
- `locale/*.json` and the icon, when declared;
- no tests, no `.env`, no credentials.

Then bump, commit and tag:

```bash
npm version patch --no-git-tag-version     # or minor / major
git add -A && git commit -m "release: v0.5.1"
git tag v0.5.1
git push origin main --tags
```

**The tag must equal `package.json` `version`.** The workflow checks this and
refuses to publish on a mismatch — a guard against tagging `v0.5.1` and shipping
`0.5.0`.

## 6. Automated publishing (OIDC)

`.github/workflows/publish.yml` publishes on a `v*` tag using npm **trusted
publishing**: GitHub signs a short-lived OIDC token, npm exchanges it for a
publish token. **No `NPM_TOKEN` secret exists, and none should be added.**

Pipeline: `install → test → pack → verify tag/version → publish --provenance →
poll until the tarball is downloadable`.

A manual `workflow_dispatch` run publishes nothing (it stops after `pack`), which
is the safe way to check the pipeline.

### Requirements that are not in this repository

The trusted publisher is registered on npmjs.com, per package:

| Field | Value |
|---|---|
| Publisher | GitHub Actions |
| Organization or user | `alfredhuang211` |
| Repository | this repository's name |
| Workflow filename | `publish.yml` (filename only, case-sensitive, with `.yml`) |
| Environment name | empty |
| Allowed actions | **must include "Allow npm publish"** |

If anything is wrong here, publishing fails with errors that do not name the
cause — see §7.

### Two workflow settings that are load-bearing

**No `registry-url` on `setup-node`.** Setting it writes
`_authToken=${NODE_AUTH_TOKEN}` into the runner's `.npmrc` and exports
`GITHUB_TOKEN` in its place; npm then prefers that credential and never performs
the OIDC exchange.

**Node 24, not 22.** OIDC needs npm ≥ 11.5.1; Node 22 ships npm 10.x.

The workflow also asserts that no `NODE_AUTH_TOKEN` and no `_authToken` line is
present, so this failure cannot come back silently.

## 7. When publishing fails

| Symptom | Cause |
|---|---|
| `E404 Not Found - PUT ...` **and** provenance signed fine | a static credential suppressed OIDC (§6). Check `registry-url` and the Node version. |
| `ENEEDAUTH` / `Unable to authenticate` | trusted-publisher config does not match: wrong repo, wrong workflow filename, wrong package |
| `You cannot publish over the previously published versions` | **authentication worked**; this version already exists. Bump it. |
| Workflow stopped after `pack`, nothing published | that was a `workflow_dispatch` run; it publishes nothing by design |

Publishing is only proven when the tarball downloads:

```bash
curl -s -o /dev/null -w '%{http_code}\n' \
  https://registry.npmjs.org/@alfredhuang211/<pkg>/-/<pkg>-<version>.tgz
```

`npm publish` prints success *before* the tarball is servable — measured 1.5 to 6
minutes on first releases. That is why the workflow polls, and why `npm view`
alone is not evidence.

## 8. Installing the result

```bash
dsh plugin --profile desktop add @alfredhuang211/<package>
```

Two things surprise people:

**A fresh release is not installed by default.** pnpm holds back versions
published recently. Naming the version explicitly makes DSH add a
`minimumReleaseAgeExclude` entry to the profile and proceed. Without a version,
you get the previous release — not an error, just an older one.

**Verify with `--dump-config`, not with the install output.** The install only
proves pnpm finished; the layer line proves the bundle actually loaded:

```bash
dsh --profile desktop --dump-config | grep '== @alfredhuang211/'
```
